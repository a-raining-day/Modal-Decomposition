二、目前涉及算法以及算法依赖
1：算法分类
算法分为：EMD家族、SSA、其他
- EMD主要是EMD的思想上去改进，没有涉及频域、调频、小波等
- SSA是以Hankel矩阵为主体，SVD为后续的办法。（目前主要是对Hankel矩阵的构建做了修改）
- 其他包括：VMD、SVMD、LMD、EWT、EFD、FMD、CEEFD。

2：算法依赖关系和家族谱系
主要存在1个依赖链和1个家族：VMD和EMD。

VMD依赖链：SVMD（逐次VMD）。把 VMD 的“一次并行提 K 个”改成“对残差逐个提 1 个”；此外在优化目标上做了扩展，要求与已有模态的频谱和残差的频谱重叠应当少。

EMD家族：CEEMD、CEEMDAN、ICEEMDAN、EEMD、RPSEMD、MEMD。
又分为：噪声、多通道、正弦。

对于EMD：给定一个信号，找上下极值点，拟合包络曲线，上下包络曲线的中值曲线为得到的IMF，信号减去IMF，继续重复迭代，直到信号单调（一般是看单调）

噪声为：EEMD、CEEMD、CEEMDAN、ICEEMDAN。
- EEMD：给定信号，生成k个不同白噪声，各自独立相加，得到k个加噪信号，用k次EMD把加噪信号分解。每个信号得到不同数量的模态（比如：imf_1,imf_2,…,imf_n），对于所有分解结果，选取当前阶的模态直接平均（比如对于k个信号的所有结果都取第 i 次的结果进行平均）（因此，虽然都是加的白噪声，原始信号一致，但是分解出来的数量不一定全一样，因此取最小数量作为k组结果的约束，残差则是 S-Σimf，为了解决这个问题，引入了CEEMD）。
- CEEMD：同上，只不过不是直接下的白噪声，而是对第 i 组信号，又各自独立地加了两次正负号的白噪声。
- CEEMDAN：不再并行（实际上EEMD、CEEMD都显然能够并行执行），是这么迭代的：给定信号，加白噪声，做EMD分解，只取第一个出来的 imf_1 作为CEEMDAN的imf_1，然后信号减去它，再重新加噪声->EMD，这样迭代。
- ICEEMDAN：不像CEEMDAN那样直接加白噪声，对于第 i 次迭代时，加的白噪声也用EMD分解到第 i 阶的 imf_i。

多通道：MEMD。
- MEMD：相当于把EMD扩展到多通道而已。

正弦：RPSEMD。
- RPSEMD：EEMD用白噪声，它用正弦信号，不过为了抵消前面加的正弦信号，后续还需要把正弦从中剔除。

四、内容
- 1.入口
当前的算法接口为Function和Class。
对于Function，其典型的运用就是Funcion.EMD(S, …,**kwargs)，之后会直接返回结果，实际上就是调用了class.decompose；对于Class，需要先获取类，对其做完定义后Class(…)，再调用其.decompose方法。
1.1. Function和Class
1.1.1. 形参输入与Config输入
对于类来说，最后会返回DecompositionResult结构，其中DecompositionResult.config是另外一个Config结构，存储了当前类的输入配置。形参输入就是直接使用参数来输入，然而由于还定义了Config，因此还需要支持Config输入。
但是形参输入和Config输入目前还需要规范的优先级定义，当同时输入进两个时，直接报错，两者应当是互斥的，而非存在可选的优先级。
1.1.1.1. 两种输入方式
形参输入：以类来说就是class(…)，之后调用class.decompose(…)，其中两处的”…”就是形参输入。以函数来说，就是function(…)，之后会直接返回结果。
Config输入：通过事先定义好的Config或者使用其余类返回的DecompositionResult.config。对于类，使用class(config)即可，之后class.decompose(…)；对于函数，使用function(S,config=config)即可。
（使用Config而非直接使用实例，是因为这样能够通过Config跨域使用，毕竟实例不一定能够被存储，而且也不必要存储，而Config作为嵌套字典，用于存储足够）
1.1.1.1.1. 对形参输入在初始化、.decompose中的约定
在初始化时，其形参输入应当是关键字的，所有的参数存在默认，不外部传入则选择默认配置。
在.deocmpose时，其形参只有S是位置参数，其余所有参数都是关键字参数：.decompose(S,*,T=None,…,**kwargs)。
1.1.1.2. 两种输入流程的约定
对于Class，两种形参都是只能用于类的初始化，不能够被用于.decompose。.decompose只能接收信号相关的参数。
对于函数，应该必须确保输入信号为第一位，即function(S,…)，其余任意。其对形参输入和Config输入的选择行为继承Class即可。
1.1.1.3. Kwargs行为规范
对于kwargs，其中不存在的键值对使用应该报错而非静默。因为在关键字传入中出现输入键的书写错误时，如果直接静默，可能会让用户认为该关键字的行为是他定义的，但实际上由于拼写错误，其行为是默认的。
1.1.1.4. 对嵌套的参数穿透的争议
对嵌套，通过**kwargs传入，不应该让下游类进一步显式继承，同时在kwargs中，提供ext_**参数与kwargs中对定义该类的参数互斥。当提供ext_**后，使用ext_**赋值给self.**，如果使用参数传入则由参数定义新类，因此self.**的类型必须是实例类。嵌套使用的类被self接管，为了解决嵌套的实例类在self而又必须让用户知道该类，在result结构中应当新增这个嵌套类在.decompose中被调用的.decompose给出的config（这是考虑到ext_**和kwargs构建的类如果采用参数记录带来的分歧），这样就能避免嵌套类所有权模糊的问题。
1.2.4.1.中还进一步讨论了嵌套类以及参数定义的问题。
1.1.1.5. 参数分类的若干问题
对于参数的分类，当应该被视为初始化的参数时，应该在初始化处，应当被视为.decompose时应该作为.decompose的参数。
然而1.1.1.6.中提出了边界模糊的参数问题。
约定.decompose只存在一个最根基参数：S，其中S是必要的，T不传入时默认为None，也就是均匀采样。这里还存在采样和时间的问题。
约定了最根基参数后，如此约定：.decompose的所有参数都是基于S的，输入不同的S，必须要改变的参数，才能够存在.decompose的形参中。除此之外的所有参数都应该放在初始化中。
1.1.1.6. 参数的并发问题与缓存
目前对参数的入口已经确定为两处：类的初始化、.decompose的输入。
然而，在.decompose中存在一些可以被视为类的一部分，但又能被视为.decompose的参数，如fs,fc等参数，以fs为例，当其表示为采样率时，作为.decompose的参数是自然的，但是作为class的初始化参数也存在一定的合理性。
这类参数的问题在于，随着S的不同而不同，但是由于数据的特性，即便是不同的输入，这类属于.decompose的参数也是可以一致的。
因此在初始化的kwargs中获取cache参数，默认为False。为True时需要在self中构建.decompose除S、T之外的所有参数缓存，当.decompose被定义好一次后，后续只需要输入S即可，其他参数将采用上次缓冲的结果。
1.1.1.7. 语义冲突的问题
语义绝对不能冲突，宁愿修改名字都不应该导致一个参数承担两种语义。这是最根本的。即便是不同的域，参数名字也应该保持不同语义不同名字。
1.1.1.8. 校验策略规范的问题
对于在类进行参数分析时（函数会继承类的行为，因此不考虑函数这部分），共有两部分：初始化和decompose。
初始化的参数被存放在__init__中，如果直接在__init__中进行检查，当参数过多时，或者需要满足更多的规则时会显示得非常臃肿，因此，我认为目前应该对Class的abc模板进行修改，新增def param_check(…) 函数，做约定。通过self.param_check(…)直接对self做检测，也并不需要输入或者输出，或者说其输出就是直接warning或者raise。
.decompose的检测则是应该由咽喉（Check_Time_and_Signal）来进行，因为.decompose实际上基本只接收S,T，或者进一步的fs（采样频率）等。不过这里牵扯到fs的多定义问题，该问题采样1.1.1.7.的约定。综上，.decompose的参数量足够少，因此不需要做专门的检测，而是直接放在.decompose内部即可。
1.1.2. Function和Class使用方法的不同（一次性和多次）
Function是通过将Class的初始化和.decompose的形参同时暴露在函数中的快速的函数式对外api，在该类的方法的形参定义中，形参必须事先把.decompose的形参确定好后才能够继续继承Class的初始化所用的形参。Function通过在内部初始化Class后再调用.decompose。Function返回完DecompositionResult之后，其生命周期就应该遵循python的约定消失。
Class需要事先做好初始化后（进行实例化），再显式调用.decompose，这样定义好Class后，后续可以多次使用class.decompose来重复执行该分解行为。其生命周期遵循python的类。但是这里对内部的嵌套方法存在1.2.4.2.的分解结果的生命周期模糊问题，以EEMD为例，当内部使用了EMD方法后，其是否应该被记录在self.emd中，否则即便外界实例化了EEMD，由于EMD是每次在.decompose中执行时同时实例化，会带来重复性问题。应该提前做好实例化或者第一次实例化后做好缓存。
1.1.3. __call__和.decompose
1.1.3.1. 当前__call__方法与.decompose方法
在python中，类定义完__call__方法指向的.f方法后，可以通过实例化后的class(…)等价于class.f(…)。
1.1.3.2. __call__带来的混淆问题
由于当前存在__call__指向class.decompose的行为，因此class的对外表现会出现混淆性问题，带来理解困难，这不应该存在，规范为不得将__call__方法指向.decompose，此外，__call__方法目前不得被使用。
1.1.4. Registry注册机制与争议
注册机制位于src/_registry.py，其核心是通过@修饰符来进行定义好后的Class的注册，注册后存在于一个字典中，在__init__中将使用Namespace类的__dict__.update()来更新这个类，并将其赋值给Class，使之对外表现为一个类。（但是在IDEA中会表现得和Class.emd这样吗？其参数会暴露吗？否则还不如Class.emd这样显式赋值）
Function的注册后续也是这样实例化一个Namespace类，来模拟表现。但是目前需要确保Function对函数的构造机制是.decompose的参数在前，其他参数都在其之后。
1.2. 大体流程
1.2.1. 记录输入，构建Config
对于Config的定义，现在已经非常明了了，为了保证1.1.1.的Config输入，将Config定义为类初始化所用的参数是很自然的。
对于Function而言，由于其内部目前假想的结构是function(S,…): Class(…); return Class.decompose(S)，因此其行为的继承是很自然的。后续Function只需要遵守好约定即可。
1.2.2. 输入咽喉
当前的所有decompose输入都需要经过Check_Time_and_Signal，因此该函数实际上是所有方法的咽喉，是必经之方法。
Check_Time_and_Signal方法当前的职责是检测信号类型、维度，以及传入的时间轴（如果传入了）的类型、维度。但是该方法还需要考虑在大数组下的表现。以及采样率和时间轴的问题，也需要考虑。
1.2.3. 算法主体与组件抽取
1.2.3.1. 算法主体和组件的边界划分
算法主体和组件的边界划分面临多个主观性问题。以EMD为例，其需要的极值点搜寻、包络拟合，实际上是可抽象出来的组件，而其算法主体实际上是循环和减法。其终止迭代的检测方法也被抽象为组件。
但是组件位置需要辨析，不是所有的组件都应该被放在Utils下，可以存放在模块中，甚至类的内部。
当该组件是常用的时，应该被放置于src/Utils下；当其是不常用的时，应该被视为Class内部的静态方法，而不能是类的函数，避免后续如果调用频繁不方便转移。
1.2.3.2. 组件抽象的位置问题
1.2.3.2.1. 应当在模块的
所有只在该方法内使用的组件，应该作为类的静态方法来定义。
如无必要，子函数不应该存在于.py中的全局域中，而是应该放于类中，作为静态方法。
1.2.3.2.2. 应当在Utils的
当被不同方法使用两次及以上时，必须放于src/Utils中，并尽可能对其性能做优化。必要时可以加入C/C++进行加速。
1.2.3.2.3. 是否应当抽象的规范问题
该问题实际上和1.2.3.1.的组件边界存在重复。除了算法主体的逻辑之外，其他涉及的方法、逻辑应该被作为类的静态方法来调用。让decompose阅读时只需要关注算法主体，而不需要考虑其他。
1.2.3.3. 算法涉及的常数配置问题（Base/ConstDefine/的问题）
当前的常数配置存在若干问题，包括全局性质的大数组的定义、模块级的常数定义都是直接被存放在src/Base/ConstDefine中，但是没有在全局的__init__中对此过多的暴露出来，这不便于调试，同时，如果让用户调试，其不同配置会带来复现性问题，我认为需要在__init__中新增Global类，专门用于暴露并定义全局配置，该类也接收Config并可通过.get_Config获取。进一步探讨在4.2.中进行。
对算法，也就是模块级别的常数定义应该被放置在哪里？从哪里被暴露出去？是由类，还是模块域中的函数？当常数被暴露后，其配置应该如何存放与输出？
相关问题会在6.1.中进一步探讨。
1.2.4. 构建返回结构与争议
1.2.4.1. 返回结构
函数由于继承至类的.decompose方法，因此这里只说类。对于类来说，.decompose最后会返回一个DecompositionResult结构。对于该结构，需要包含IMFs,Res以及其他的Config、嵌套类实例的.decompose的Config，Config的下游子类（如EMDConfig这类）需要dataclass进行冻结。
1.2.4.2. 分解结果的生命周期模糊问题
对于分解结果目前有IMFs,Res,config,Info，这部分的更详细讲解在3.1.1.中。其中，info记录关于S迭代或最终结果相关的衍生，而config则是对初始化的记录。
目前对于IMFs,Res来说，是否存在class中？即便后续牵扯到4.7的画图问题，但是如果存于类中，那么又返回IMFs和Res，会让人认为生命周期实际是在返回中，但当引入存储后，class内部也会存在，小数组还好，当输入为大数组时，其分解结果会变得更大，此时如果还要保存，那对用户来说是隐蔽的占用空间。
综上，我认为不该记录在类的内部，同时，对4.7的画图问题，我认为需要独立出来作为一个画图函数，需要显式地输入结果，可以输入参数或者整个Config，但是不能作为类的内部函数直接调用。
类只接管初始化的参数的生命权，并同步为类的生命，而不能再由用户独立删除。而类的所有分解结果，类不做任何的保留，整个所有权全部转交给用户。

2.1.1. abc和dataclass
目前对dataclass的使用主要是利用其frozen机制进行冻结。目前使用abc的类有：DecompositionResult、Config的下游（不包括Config）。
对abc的使用有：Decomposer。主要用于强制实现.decompose方法和.param_check方法。
2.1.2. Config定义与争议
目前是Config不做约束，其下游各分支由dataclass(frozen=True)进行冻结。Config需要获取初始化的所有必要参数，但是由于部分参数是kwargs.get，直接对__init__读取，只会得到不完全的kwargs，因此建立了config_construct_start函数和config_construct_end函数。start在__init__中前面的初始参数全部定义完后被调用，记录当前的self.**初始化参数，之后在.decompose处必须调用end来获取最新的cfg。这样就保证cfg是绝对最新的了。
代码如下：
class Decomposer(ABC):
    def __init__(self):
        self.__snapshot = None
        self.__config_construct_success = False
　　def config_construct_start(self) -> None:
        internal={"_Decomposer__snapshot",
"_Decomposer__config_construct_success"}

        self.__snapshot = set(vars(self)) - internal
        self.__config_construct_success = True

    def config_construct_end(self) -> dict:
        if (not self.__config_construct_success) or (self.__snapshot is None):
            raise PreError("the pre-config isn't constructed yet, use `config_construct_start` at the beginning of __init__")

        missing = [k for k in self.__snapshot if not hasattr(self, k)]
        if missing:
            raise PreError(f"the following config keys were recorded at __init__, but are not set as attributes on self: {missing}")
        return {k: getattr(self, k) for k in self.__snapshot}

2.1.3. Cache的职责和定义，模块注册-缓冲与注册-缓冲的不同路径争议
对于Cache，主要用于导入外部的重库（如：SciPy、scikit-learn），但是对于根基库并不需要Cache进行缓冲。
Cache的主要重用是通过try-except导入重型外部库的模块，为了避免多次try-except带来的开销，因此采用flag机制，通过if-flag包裹try-except，避免多次try-except的开销，if至少比try-except快，这也是Cache的主要职责。
该部分和4.1.2.的规范要求一致。
