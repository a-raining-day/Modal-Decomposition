# VMD 大数组 / 分块迭代 / 并行 实测报告

- 日期: 2026-03-04
- 范围: `VMD_new_new.py`(实验分支)、`tests/comparison/bench_vmd_large.py`, 以及**并行更新**
  与**频轴分块 + 外存**两条路线的评估
- 一句话结论: **并行(模态独立/分块 Jacobi)已否决**(数学上会发散, 多线程无净收益);
  **频轴分块/外存能压内存但不能加速, 且对 VMD 无用** —— VMD 的内存墙是
  "K 个模态谱 + 一次全局 FFT + 必须返回的模态"三项, 与迭代策略无关;
  唯一确定该采纳的是**去掉整块 `u_prev`**(省 ~38% 内存, 零代价)。

本报告刻意保留**未采用方案的全过程与数据**, 以免后人重复踩坑。

## 1. 实验一: 并行更新(结论: **不采用**)

### 1.1 实现的语义

| 配置 | 更新顺序 |
|---|---|
| `parallel=False` | 顺序 Gauss-Seidel(现状, 与 vmdpy/MATLAB 一致) |
| `parallel=True, group=1` | 每个模态独立, 全部用**上一轮**值(纯 Jacobi —— "最自然的并行情形") |
| `parallel=True, group=k` | 组内顺序(组内已更新值参与), **组外取上一轮值** ⇒ 组间互不依赖, 可并发 |
| `group>=K` | 退化为"全模态一组" = 顺序更新 |

并行实现为 `ThreadPoolExecutor`(numpy 大数组运算会释放 GIL), 并发上限默认取可用 CPU 的 2/3。

### 1.2 过程中发现并修掉的实现 bug(重要)

第一版块 Jacobi 的残差**漏掉了"组内尚未更新模态的上一轮值"**(应为
`Σ_{i≠k}û_prev + Σ_{i<k,同组}(û_new − û_prev)`)。后果: `g=K` 实际在解另一个下三角系统,
显示"比顺序快 2.2×"并只用 18 次迭代"收敛" —— **假象**。修正后 `g=K` 与顺序更新逐位一致
(`max|ΔIMFs| ≈ 1e-15`, `max|Δω| ≈ 3e-17`), 也证明块实现本身是对的。

教训: 这类"更快"的观测必须用"迭代数 + 末态一致性"双重复核, 不能只看墙钟。

### 1.3 数据

**(a) 正确性: 小分组/纯 Jacobi 会发散**

| 场景 | 结果 |
|---|---|
| K=3 三音信号, group=1 (纯 Jacobi) | 500 次迭代后残差 **9.4e41**, 未收敛 |
| K=5, group=1 | 直接溢出 **NaN** |
| K=16 (N=65536), group=2 / group=4 | 收敛到 **NaN** |
| group≥K | 与顺序更新逐位一致 |

原因是可解析的: 模态独立更新即 VMD 线性系统的 Jacobi 迭代, 迭代矩阵谱半径约
`(K-1)/(1+α(f-ω)²)`, 在频带重叠处(`f≈ω`)远大于 1 ⇒ 必发散。**顺序更新是 VMD 算法的一部分,
不是实现细节。**

**(b) 即使收敛, 迭代数也暴涨**

| K=3, N=4096 | 迭代数 | 残差比 |
|---|---|---|
| 顺序 | **35** | 8.9361e-03 |
| group=2 | **447**(12.8×) | 8.9362e-03 |
| group=3 | 35 | 8.9361e-03 |

**(c) 多线程无净收益**(同公式、固定 100–200 次迭代, 1/2/4/8/21 线程)

```
N=4096  K=3 : w=1 0.0068s → w=2 0.0153s → auto 0.0211s   (顺序 0.0059s, 全面变慢)
N=16384 K=3 : w=1 0.0668s → auto 0.0431s  (比自身快 1.55×, 但仍慢于顺序 0.0498s ⇒ 净 1.16×)
N=65536 K=3 : w=1 0.1875s → auto 0.1514s  (顺序 0.1202s, 仍更慢)
N=65536 K=16: 顺序 1.436s; 唯一超过 1× 的 g=4,w=8 为 1.11× —— 而该配置在同一信号上 NaN
```

微观基准(纯更新扫描, 200 次取均值): 向量化 Jacobi 因 (K,N) 大临时数组反而比顺序慢
(0.35–0.97×), 线程普遍 0.28–0.87×。单次扫描只是 (N,) 上的几个向量运算, 线程调度与内存带宽
成本占主导。

### 1.4 结论

**并行不采用**: 模态独立更新在数学上对 VMD 发散, 分块 Jacobi 即使收敛也需 10× 以上迭代,
多线程在实测中无净收益。相关结论已写入 `VMD_new.py` docstring 的
"并行更新 (已评估, 未采用)" 一节。需要并行时, 收益在**多信号批处理**层面(多个 `decompose`
之间), 而不是单个分解的内层循环。

## 2. 实验二: 频轴分块迭代 + 外存(结论: **不加速, 仅在大到必须落盘时才有意义, 而 VMD 到不了那里**)

### 2.1 实现

`VMD_new_new.py` 新增 `engine={ram,chunked,auto}` + `chunk_size` + `out_of_core`, 并在两条引擎上
共同做两处内存优化:

1. **去掉整块 `u_prev` (K,N) 拷贝**: 顺序更新只需要"当前模态的旧值", 一个 (N,) 暂存即可
   (K=5、1GB 输入时省约 10.7 GB);
2. **`λ̂` 只保留 `λ̂/2` 一份**(乘以 0.5 是 2 的幂缩放, 与 IEEE 舍入可交换, 故与保留 λ̂ 逐位相同)。

分块路径: 频轴按 `chunk_size` 切片, 每块内顺序更新 K 个模态; 两个归约(ω 的功率加权均值、
`Σ_k‖Δû_k‖²`)改为逐块部分和再相加; `out_of_core=True` 时镜像/单边谱/模态谱/λ̂ 全部走临时
memmap, 分块粒度与落盘时机复用 `Utils.Chunk` / `Utils.Memory` 的既有策略。

### 2.2 等价性验证

| 断言 | 结果 |
|---|---|
| `engine="ram"` vs `VMD_new` | **IMFs 与 Res 逐位相同** ✓ |
| `engine="chunked"` (chunk=1MB…256, 含 ooc) vs ram | `max|ΔIMFs| ≈ 1e-15`, `max|Δω| ≤ 8e-17`, 迭代数相同 ✓ |
| `out_of_core=True` vs `False` (同块长) | 数值完全相同 ✓ |
| `_fill_mirror` 分块写入 vs `_mirror_signal` | 所有 N/块长组合逐位相同 ✓ |

过程中修掉一个**真实 bug**: `_fill_mirror` 的左镜像按源索引分块(`dst[a:b] = f[a:b][::-1]`),
只在单块时正确, 分块会错位——表现为 chunk=256 时 `n_iter` 21 vs 14、`max|ΔIMFs|` 1.03。
改为按目标区间对齐(`dst[a:b] = f[L-b:L-a][::-1]`)后全部一致。

### 2.3 实测(VMD 300MB 实验组中止前的数据)

固定 10 次迭代, 每配置独立子进程:

| config | 1 MB | 10 MB | 300 MB |
|---|---|---|---|
| `vmd_new` (原版) | 0.09 s / 64 MB | 1.21 s / 631 MB | 99.6 s / **10148 MB** |
| `new_ram`(去 u_prev) | 0.09 s / 40 MB | 1.23 s / **391 MB** | 46.5 s / 10099 MB |
| `new_chunk`(分块) | 0.15 s / 48 MB | 1.54 s / **323 MB** | 57.5 s / 7236 MB |
| `new_ooc`(分块+外存) | 0.15 s / 46 MB | 1.57 s / 321 MB | 52.2 s / 7236 MB |
| `new_auto` | 0.08 s / 40 MB | 1.08 s / 391 MB | 49.0 s / 7236 MB |

- **内存**: 去 `u_prev` 立竿见影(10 MB: 631→391 MB, −38%); 分块再降到 323 MB(−49%)。
- **速度**: 分块**比内存内慢 15–25%**(10 MB: 1.54 vs 1.23 s), 外存与内存内分块同速(小尺寸下
  临时文件被页缓存吸收)。
- **300 MB 的计时受换页污染, 不可信**(见 §4); 内存数字可信。
- 300 MB 组 5 个配置的残差比完全一致(3.23e-01) ⇒ 大尺寸下各引擎仍等价(旁证)。

### 2.4 内存模型与投影(修正后的公式)

RAM 路径峰值 ≈ `(56K + 104)·N` 字节 ≈ **(7K+13) × 输入大小**:
300 MB/K=3 模型 11.7 GB vs **实测 10.1 GB** ✓(小尺寸实测偏大, 因解释器/分配器基线占比高)。

| 输入 | K | RAM 路径 | 分块+外存 | 外存下限构成(谱 / 逆变换 / 结果) |
|---|---|---|---|---|
| 100 MB | 3 | 3.91 GB | 0.99 GB | 0.20 / 0.39 / 0.39 |
| 300 MB | 3 | 11.72 GB | 2.94 GB | 0.59 / 1.17 / 1.17 |
| 500 MB | 3 | 19.53 GB | 4.89 GB | 0.98 / 1.95 / 1.95 |
| 1 GB | 3 | **40.0 GB** | **10.0 GB** | 2.00 / 4.00 / 4.00 |
| 1 GB | 1 | 26.0 GB | 8.00 GB | 2.00 / 4.00 / 2.00 |

**三处分块救不了的内存**(这才是 VMD 的墙):
1. **FFT 地板**: `np.fft` 是全局变换, 镜像 2N + 单边谱 N 必须同时驻留; 且实测
   `np.fft.rfft` 还需一份 **N 点复数 scratch**(1 GB 输入 ⇒ 4.1 GB 峰值, 见 FFT 报告 §4.1);
2. **返回契约**: `IMFs`(K,N) 与 `Res` 必须常驻内存(1 GB/K=3 ⇒ 4 GB);
3. **逆变换**: 每模态 (N+1) 复数 + 2N 实数(可逐模态复用, 已是下限)。

**外存能省"匿名内存", 但不能省"工作集"**: 300 MB 实测 7236 MB 远高于模型 2.94 GB ——
memmap 的页缓存被 Windows 计入进程工作集, 内存吃紧时被裁剪 ⇒ 退化为 I/O。

### 2.5 结论

- 分块**不加速**(慢 15–25%), 只在小尺寸下省一点内存; **外存是 I/O 瓶颈**:
  1 GB/K=3 每迭代约 19 GB 读写, 百次级迭代不可行(实测 10 次迭代已 52 s);
- 因此 **VMD 不引入分块/外存**。真正值得合回 `VMD_new` 的是 **去掉 `u_prev` 的 −38% 内存**;
  真要支持 GB 级输入, 可行方向是 **float32(NumPy 2.x 原生 complex64, 内存减半)**、
  **降低 K**、或**改返回契约把模态直接落盘** —— 都不是分块能解决的。

## 3. 事故记录: 内存上限判定失效, 把机器拖入换页(**必须记录**)

### 3.1 发生了什么

`bench_vmd_large.py` 首版给每个子进程设了 **2.6 GB 的 RSS 上限**, 由父进程每 50 ms 采样
`psutil` 的工作集判定。跑 300 MB 组时**判定始终认为"未超限"**, 而进程实际提交内存顶到
**10148 MB**, 整机被拖入内存压缩/换页(`MemCompression` 1.4 GB), 被用户发现后中止。

### 3.2 根因(两条)

1. **用工作集(RSS)做上限是错的**: Windows 在内存压力下会**主动裁剪工作集**, 采样到的 RSS
   可以长期低于真实占用; 真正该盯的是**提交内存**(private/vms)。
2. **`Utils.Memory` 的判定也失效**: 它只看 `psutil.virtual_memory().available`(当时 3.38 GB),
   而页面文件另有 15.28 GB 空闲 ⇒ "可提交 18.66 GB"。于是"提交 10 GB 而物理只剩 3 GB"被判为
   内存充足。**这是库级缺陷, 已修**(见 `docs/FFT_Backend_Report.md` §5):
   新增 `memory_budget()`(物理可用与可提交余量取小, 再扣 25% 系统余量与调用方占用)、
   `get_commit_available()`、`get_process_memory()`, 快照 TTL 1.0 s → 0.25 s。

### 3.3 修正后的协议(现基准脚本统一采用)

1. **跑前过预算闸门**: `Memory.memory_budget(预计峰值)`; 不通过就记 `over_budget` 并且
   **不分配** —— "先分配再被杀"是最贵的失败方式;
2. **监控提交内存**而非工作集, 超限即杀;
3. **投影预检**: 用 `_project_bytes` 先算该配置必然超预算就直接跳过(我这次是先跑后算, 顺序错了);
4. 逐条记录状态(`ok` / `over_budget` / `commit_cap` / `timeout` / `unavailable`)。

## 6. 结论汇总(可直接执行的建议)

1. **采纳**: `VMD_new` 去掉整块 `u_prev`(内存 −38%, 数值逐位不变)。
2. **不采纳**: 并行更新(发散 / 10× 迭代 / 线程无收益); 频轴分块与外存(减速 15–25%,
   且 VMD 的墙在 FFT 与返回契约上, 分块够不着)。
3. **下一步值得做的**: float32(NumPy 2.x 的 `rfft(float32)→complex64`)可把 §2.4 的所有项减半;
   以及多信号批处理并行(收益在 `decompose` 之间, 不在内层循环)。
4. **教训固化**: 大数组实验一律"预算闸门 + 提交内存监控 + 投影预检", 且"更快"的观测必须用
   迭代数与末态一致性复核。
